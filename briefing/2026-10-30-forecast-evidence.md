# Forecast evidence flow and producer contract

**Research date:** 2026-10-30. **Purpose:** define the minimum evidence the Frankfurt dashboard can show for one selected forecast hour, and the records the ML/CLI producer must persist so that view can be inspected later. This is a research proposal grounded in the current branch contracts, not an implementation or a claim that these fields already exist.

**Checkout scope correction:** source inspection for this briefing was performed on branch `hugo/forecast-ui-spec` at `74a56044aa1317fcb31eed105fb9f0be02931c30`. Statements below about fields/artifacts absent from that inspection describe that snapshot only. A later GitHub snapshot reported during research, `947ea972046483c92e873c6e30787f74d2b34b46` includes `ml/train.py`, `predict.py`, `features.py`, `quality.py`, fitted models and `QualityResult`. Those later implementation details were not re-inspected here; this briefing does not claim they are absent. The producer fields listed remain a proposed UI trace contract to reconcile with that implementation.

## Recommended visual: follow the evidence

Show one left-to-right path for the selected hour. Each box is clickable; its detail panel shows the exact saved record and source. A separate evaluation lane sits below the forecast path so historical references and scores cannot be mistaken for live inputs.

```text
FORECAST PATH (one issue time, one selected valid hour)

[Source snapshots] -> [Feature values + transformations] -> [Model outputs] --+
          |                         |                     [Rules baseline] --+--> [Forecast card]
          |                         |                                          |
          +-------------------------+------------------------------------------+
            source IDs / UTC times / missing state / model, code and rules versions

EVALUATION PATH (separate, only when reference data and evaluation artifacts exist)

[Recorded OD reference] -----> [OD evaluation: n, accuracy, Brier, reliability]
[Inferred runway-18 ref] -----> [R18 evaluation: n, accuracy, Brier, reliability]
```

This is an evidence trace, not an explanation generated by the model. Values are shown because the producer captured them. If a value or lineage record was not captured, show **Unavailable**; do not infer it from a score, label, feature name, or neighboring hour.

## What the inspected checkout's dashboard contract can show, and what it needs

The [ForecastResponse contract](../web/src/lib/forecast-types.ts) in the inspected checkout provides issue time and mode, weather-source string, model/rules version strings, current OD, 48 hourly outputs, probabilities, certainty, wind and gusts, calculated tailwinds, and rule outputs. Each hour has a UTC valid time and lead. That inspected contract does not identify exact source records, retrieval time, source/model initialization time, raw feature vector, transformation steps, source-data digest, code/model artifact digest, or per-target reference provenance. Its `observed` row requires both OD and runway-18 values even though the data brief says OD can be DFLD-recorded while runway-18 usability is inferred from METAR and rules. The durable UI contract and its intended meanings are described in [WP5 design](../openspec/changes/wp5-ui-timeline/design.md) and [WP4 producer brief](../briefs/hk-cli.md). These are checkout findings, not an assertion about current main.

## Required producer records: three distinct layers

These are a proposed producer contract for the backend team to consolidate. They can be emitted as a forecast plus a sidecar trace, or persisted in an equivalent immutable record store. Every record must be joinable; a single confidence number is not enough to recreate the path.

### 1. User-facing forecast output (per hour, per target)

The existing JSON remains the compact serving payload. Add or agree a stable `forecast_id`; every hour remains keyed by `(forecast_id, valid_time, lead_h)`. The forecast must preserve both output targets independently:

- OD: `p_od25`, call `od`, threshold/decision rule, and target label meaning.
- Runway 18: `p_18_usable`, call/threshold if supplied, and explicit departure-usability meaning.
- Existing `certainty` with its precise definition and `next_change.p` with the meaning of probability of the new direction at that hour.
- Wind, gust, tailwinds, rules outputs, issue time, mode, weather source, model and rules versions.

Do not let one target's provenance bleed into the other. A recorded OD does not establish recorded runway-18 usability. The repository says the OD evaluation can use DFLD-recorded directions where covered, while runway-18 target labels are inferred from METAR and rules; see the [ML brief](../briefs/hk-model.md), [WP5 design](../openspec/changes/wp5-ui-timeline/design.md), and [timeline spec](../openspec/changes/wp5-ui-timeline/specs/ui/timeline/spec.md).

### 2. Inference instrumentation and input snapshots (mandatory for a clickable trace)

Minimum run-level record:

- Stable `inference_id`, `forecast_id`, `input_snapshot_id`; `issued_at` and `input_cutoff_at` in UTC; `mode`; code revision; feature-schema and transform version; model artifact ID/version and digest; rules version and digest; source/model selection; completion status.
- For every source record: source name/product, immutable local artifact URI or source record key, content digest, request/selection metadata, station or grid location, variable names/units, source valid/report time, NWP run initialization time when known, fetch/retrieval time, availability/freshness observation, and per-field missing/error status.
- For every hourly prediction and target: exact feature snapshot actually passed to the estimator (feature names/schema and values in their applied order), raw pre-transform values, transformations/encoding/defaults applied with version, and explicit flags identifying missing values, imputations, clamps or fallback substitutions. Preserve lineage from each feature back to its source snapshot/field. If preprocessing is deterministic and versioned, storing the exact post-transform vector plus raw inputs and versioned transform reference is the minimum needed to replay; retaining both is safer for a hackathon artifact.
- Per target prediction: estimator/model artifact ID, target ID, probability, threshold and resulting call, inference status, and a trace join key. If inference fails, preserve the failure state; do not fabricate a probability.
- Per-hour rule computation: actual observed/forecast wind inputs used, ruleset ID/digest, threshold/formula version, starting state, any pending tolerance/hysteresis state, result and missing-input state. Do not infer this trace afterward from a final rule call if the original inputs/state were not persisted.

Use the exact source-reported timestamps where available. For Open-Meteo, `_previous_day1` and `_previous_day2` indicate 24 h and 48 h fixed lead offsets, while `Best Match` may select a model; the API docs describe update and initialization metadata separately. Record the selected product/model and its run-initialization metadata when returned, rather than calling the offset a complete exact run identity. See the [Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api) and [model update metadata](https://open-meteo.com/en/docs/model-updates), accessed 2026-10-30. For observed METAR/ASOS data, preserve station, report/observation time and raw source reference alongside parsed wind; IEM documents its [ASOS/METAR request service](https://www.mesonet.agron.iastate.edu/api/) (accessed 2026-10-30). DWD likewise instructs users to retain station and supplied metadata; see its [CDC data readme](https://opendata.dwd.de/climate_environment/CDC/Readme_intro_CDC_ftp.pdf), accessed 2026-10-30.

### 3. Training and evaluation artifacts (separate from one inference)

Store immutable training/evaluation evidence separately and reference it from the UI only when present:

- Training run ID, model artifact digest, training data snapshot IDs/digests, training cutoff/period, feature schema/transform versions, label definitions and per-target provenance/coverage, code revision, and fit configuration sufficient to identify the produced artifact.
- Walk-forward fold IDs with train/test periods and counts; evaluation target, lead, and method (model, rules, persistence); per-target sample count, accuracy and Brier score. Preserve excluded/missing rows and reference coverage; do not count missing labels as errors or hits.
- Reliability table per named probability event and lead: bin range, mean predicted probability, observed event frequency, `n`, evaluation fold/period and reference provenance. The WP8 requirement explicitly calls for probability-vs-observed-frequency tables. A bin for “both calls correct” is a separate event; it cannot be inferred from either individual probability.
- Next-change timing metrics only when an explicit event-matching definition and reference exist; distinguish observed direction-change timing from stable-hour classification.

The project currently requires walk-forward evaluation and Brier scores at 1/6/24/48 h in [WP3 spec](../openspec/changes/wp3-model-backtest/specs/forecast/model/spec.md) and reliability evidence in [WP8 spec](../openspec/changes/wp8-model-quality/specs/evaluation/model-quality/spec.md). Scikit-learn describes reliability diagrams as bins of average predicted probability against fraction of positives, and warns that Brier loss combines reliability, resolution and uncertainty; a lower Brier score alone does not prove better calibration. See [probability calibration](https://scikit-learn.org/stable/modules/calibration.html) and [calibration_curve](https://scikit-learn.org/stable/modules/generated/sklearn.calibration.calibration_curve.html), accessed 2026-10-30. Brier's original paper is [AMS, 1950](https://doi.org/10.1175/1520-0493(1950)078%3C0001%3AVOFEIT%3E2.0.CO%3B2), accessed 2026-10-30.

## A typed trace shape and illustrative selected-hour record

The following is a suggested logical shape, not a required serialization format. `null` means unavailable only when paired with a status/reason; omission must not silently imply false, zero, calm, or a successful fallback.

```ts
type Availability =
  | { status: "available" }
  | { status: "missing"; reason: string }
  | { status: "stale"; ageSeconds: number; reason?: string }
  | { status: "fallback"; reason: string; fallbackId: string }
  | { status: "error"; reason: string };

type Target = "od25" | "runway18_usable";
type Provenance = { kind: "recorded" | "inferred" | "published" | "unknown";
  sourceId?: string; referenceTime?: string; method?: string };

interface ForecastTrace {
  forecast_id: string;
  inference_id: string;
  input_snapshot_id: string;
  issued_at: string;             // UTC
  input_cutoff_at: string;       // UTC
  valid_time: string;            // UTC
  lead_h: number;
  mode: "live" | "hindcast";
  code_revision: string;
  model: { version: string; artifact_id: string; sha256: string; status: string };
  feature_contract: { schema_version: string; transform_version: string };
  rules: { version: string; sha256: string };
  sources: Array<{ source_id: string; product: string; request_or_file_ref: string;
    sha256: string; location: string; variables: string[]; units: Record<string,string>;
    valid_or_report_time: string | null; run_init_time: string | null;
    retrieved_at: string; availability: Availability }>;
  features: { raw: Record<string, number | string | boolean | null>;
    transformed_order: string[]; transformed_values: Array<number | string | boolean | null>;
    missing_or_imputed: Record<string, Availability>;
    lineage: Record<string, Array<{ source_id: string; field: string }>> };
  rule_result: { inputs: Record<string, number | string | null>;
    pending_hysteresis_minutes: number | null; output_od: "25" | "07";
    output_r18_usable: boolean | null; availability: Availability };
  predictions: Array<{ target: Target; probability: number | null;
    call: string | boolean | null; threshold: number | null;
    availability: Availability }>;
  derived: { certainty_margin_score: number | null;
    certainty_definition: string; next_change_probability_semantics: string };
  references?: Array<{ target: Target; value: string | boolean | null;
    provenance: Provenance; availability: Availability }>;
}
```

Illustrative only; none of these numbers describe a real issue or source record. In this example, source `availability: available` means retrieval succeeded, not that historical availability at the issue-time cutoff was established. Retrieval is ten seconds after the cutoff and run initialization is unknown, so historical availability remains unverified and this example does not pass an as-of-time audit. The `references` section represents later evaluation enrichment joined to the forecast, not information present in the immutable issuance record:

The example's score is arithmetic only: `min(|2×0.8−1|, |2×0.7−1|) × 100 = 40`. It is a **margin score**, not measured accuracy, calibrated probability of correctness, or evidence that both calls are right. The current formula and the special next-change probability semantics are defined by the [forecast type and producer brief](../web/src/lib/forecast-types.ts) and [WP4 brief](../briefs/hk-cli.md). The `p` attached to a next-change row represents the probability of the new direction at that hour, not the probability of a switch event; the [WP5 spec](../openspec/changes/wp5-ui-timeline/specs/ui/timeline/spec.md) requires that wording.

## Confidence, calibration and explainability boundaries

- **Show probabilities as model outputs.** Label them `P(OD 25)` and `P(runway 18 usable)` and show the target definitions. These values are not evidence of calibration on their own.
- **Show certainty as a score.** The contract computes `round(100 × min(abs(2*p_od25−1), abs(2*p_18_usable−1)))`. It is twice the smaller distance from 0.5 across the two output probabilities, scaled to 100. It is not empirically measured accuracy or an 80% chance both calls are correct. Keep it visually separate from each probability and from backtest accuracy; the [WP5 spec](../openspec/changes/wp5-ui-timeline/specs/ui/timeline/spec.md) explicitly preserves this distinction.
- **Show validation by target and held-out period.** OD results should identify recorded DFLD references and their coverage/exclusions; runway-18 results should say inferred when METAR+rules supplied the target. Do not combine them into one accuracy figure without a separately defined joint target and rows where both references exist. Walk-forward test periods must follow their training periods; include `n`, lead and label source. This follows the [WP3](../openspec/changes/wp3-model-backtest/specs/forecast/model/spec.md) and [WP8](../openspec/changes/wp8-model-quality/specs/evaluation/model-quality/spec.md) requirements.
- **Show calibration only from saved calibration evidence.** A reliability view must name the event: calibrate `p_od25` against OD 25 occurring and `p_18_usable` against runway 18 being usable. Prediction correctness requires a separately defined confidence transformation; joint correctness requires separate evidence. Include the probability being assessed, lead, bins, mean prediction, observed frequency, sample count, time period and target provenance. Do not derive calibration bins from `certainty`; do not imply unseen performance from training fit. Scikit-learn documents both bin-based reliability curves and the fact that Brier score alone does not isolate calibration.
- **Do not add a generated rationale.** Persisted inputs, transforms, model identity, probabilities and rules results support an auditable trace without retraining or narrative generation. Optional feature attribution must be an actually computed artifact with method, target, evaluation data and version attached. Global permutation importance is not a faithful per-hour reason; correlated inputs can mask one another, as the scikit-learn [permutation-importance guide](https://scikit-learn.org/stable/modules/permutation_importance.html) and [correlated-feature example](https://scikit-learn.org/stable/auto_examples/inspection/plot_permutation_importance_multicollinear.html) explain (accessed 2026-10-30). If no valid per-instance contribution is computed, show the actual feature values and say “No per-hour attribution available.” Never invent top drivers from the model name, weights, or one probability.

## Missing, stale and fallback states

1. Keep `available`, `missing`, `stale`, `fallback`, and `error` distinct at source, feature, target and reference levels. A missing wind direction is null with its reason; do not replace it with zero degrees. A missing reference is not a negative target.
2. Preserve age using `retrieved_at` versus source report/valid time and current display time. The repo says no automatic cadence or freshness SLA has been verified. Show age and stale status based on supplied producer policy; do not invent a stale cutoff. `mode: live` means forecast mode, not proof of a live operational feed.
3. A rules fallback must identify that model path and the origin of its probabilities/calls. The project specifies `model_version: "rules-fallback"`; the UI must not present fallback probabilities as trained-model results. If the CLI cannot provide defensible probabilities under fallback, mark them unavailable rather than fabricating model confidence.
4. An input cutoff is necessary to test the no-look-ahead rule: observed inputs must be at or before issue time and forecast runs must have been available/issued by the cutoff. Record issue/valid time separately. A source's later retrieval time does not prove it was available at the historical issue time.
5. Store and join UTC timestamps; display Berlin local time with the correct UTC offset. Preserve repeated DST hours as distinct UTC records, per [WP5 requirements](../openspec/changes/wp5-ui-timeline/specs/ui/timeline/spec.md).

## Mandatory MVP vs optional explanation

**Mandatory for the evidence view:** stable forecast/inference/snapshot/hour/target IDs; issue, valid and cutoff times; source identifiers and immutable references/digests with source and retrieval metadata; exact raw and actual transformed feature values with versioned transformation/schema; model artifact and code identity; per-target probabilities, thresholds, calls and status; exact rule inputs/version/state/outcomes; distinct target reference values and provenance; and evaluation/calibration records with target, period, lead, count and missingness. This is instrumentation and snapshot persistence, not retraining or narrative generation.

**Optional, show only when computed and validated:** per-instance feature contributions with a named algorithm and model compatibility; grouped permutation results; confidence intervals or uncertainty intervals with a stated method and coverage evidence; richer attribution charts. These are not recoverable from current probabilities and must not be fabricated. A single score cannot reconstruct sources, feature values, transformations, rule outcomes, versions or feature contributions.

## Quick challenges for the trace review

1. **Can I select an hour and recover the exact issued forecast?** Join `forecast_id → inference_id → input_snapshot_id → valid_time/lead_h`; confirm model, code, feature schema, rules and source snapshot digests.
2. **Can I inspect real model inputs?** Compare the persisted transformed vector, ordered schema and missing/imputation flags to the source-linked raw feature values. If only the output probability is stored, mark the feature trace unavailable.
3. **Can I reproduce the rule baseline?** Find the exact wind values, starting OD/hysteresis state, rules version and outputs. A final `rule_od` alone is not enough.
4. **Can the two targets disagree in provenance?** Show DFLD-recorded OD separately from METAR/rule-inferred runway-18 reference; a missing runway-18 label must remain unavailable.
5. **Can a reviewer distinguish probability, score and evidence?** The OD and runway-18 probabilities are model outputs; certainty is the defined margin; accuracy/Brier/reliability come from named held-out evaluation data.
6. **Can a stale or fallback input be seen?** Its source, age/status, substituted value and fallback reason must be explicit, with no silent default.
7. **Can a claim of “why” be audited?** If no captured per-instance attribution exists, UI says unavailable and displays inspected inputs; no generated narration or inferred driver list appears.

## Material unknowns

- Exact trace fields, schema versions, IDs, digests and persistence location are recommendations for backend/ML/UI owners to reconcile with current main; this briefing does not audit whether main implements them.
- The illustrative JSON is not observed inference evidence. It is example data; the current-main implementations and generated walk-forward/reliability outputs were not re-inspected here.
- Exact source run initialization and historical availability may not be returned by every selected API product. If absent, persist `null` with a reason; do not reconstruct an exact run identity from a fixed lead offset.
- A freshness threshold, source-at-issue availability proof, full DFLD coverage/exclusion summary, and a provenance-compatible nullable per-target reference shape remain owner decisions/data questions. The current briefing and specs establish the need but do not resolve these contracts.
- Per-instance feature attribution was not specified by the inspected UI contract or verified in this research. Feature-value inspection and lineage can be delivered without it; any later attribution method needs its own documented semantics and validation.
